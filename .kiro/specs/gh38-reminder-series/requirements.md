# Requirements Document

## Introduction

Reminder Series enables users to define a repetition frequency when creating or editing reminders, so that calendar events are automatically generated on a recurring schedule. The feature supports four frequencies: never (default, current behavior), every week, every month, and every year. When a reminder with a series is assigned to a calendar event, the system generates subsequent calendar events at the specified cadence, adjusting only the start and end dates while preserving all other event fields. Shifts are not affected by this feature. The feature applies to both the React Web PWA and the Android App, follows the offline-first architecture, and supports bidirectional synchronization for subscribed users.

## Glossary

- **Reminder**: A named reminder definition containing a name, icon, background color, active status, and now a repetition frequency. Used as a template for calendar event creation.
- **Reminder_Series**: The repetition configuration on a Reminder, specifying how frequently calendar events should be automatically generated from that reminder.
- **Series_Frequency**: The enumerated value representing the repetition interval. Valid values: `never`, `weekly`, `monthly`, `yearly`.
- **Reminder_Form**: The UI component used for both creating and editing a reminder, containing all configurable fields including the series frequency selector.
- **Reminder_Store**: The local persistence layer (IndexedDB on Web, SQLite on Android) that stores all reminder records on the device.
- **Calendar_Event**: A scheduled occurrence spanning one or more days and a time range, linked to either a Shift or Reminder definition.
- **Event_Store**: The local persistence layer (IndexedDB on Web, SQLite on Android) that stores all calendar event records on the device.
- **Source_Event**: The original calendar event created by the user that serves as the template for generating series occurrences.
- **Series_Occurrence**: A calendar event automatically generated by the system based on the Source_Event and the reminder's Series_Frequency, with adjusted start and end dates.
- **Propagation_Modal**: A dialog that asks the user whether to propagate template changes (including repetition changes) to existing calendar events for the current year.
- **Sync_Service**: The cross-cutting synchronization module responsible for pushing and pulling reminder and calendar event records to/from the backend API.
- **Current_Year**: The calendar year in which the modification is made (January 1 through December 31 of the year containing today's date).
- **Reminders_Page**: The dedicated UI page accessible via the "Reminders" navigation item that lists all user-created reminders.
- **Predefined_Palette**: A fixed set of 45 colors (9 families × 5 shades) available for reminder background selection.

## Requirements

### Requirement 1: Add Series Frequency Field to Reminder

**User Story:** As a user, I want to specify how often a reminder repeats when I create or edit it, so that calendar events are automatically generated at the chosen interval.

#### Acceptance Criteria

1. THE Reminder_Form SHALL include a mandatory Series_Frequency selector field that presents exactly four options: "Never" (default), "Every week", "Every month", and "Every year".
2. WHEN the user creates a new reminder, THE Reminder_Form SHALL pre-select "Never" as the default value for the Series_Frequency field.
3. WHEN the user submits the Reminder_Form with all required fields valid, THE Reminder_Store SHALL persist the selected Series_Frequency value as part of the reminder record and update the record's `modifiedAt` timestamp to the current UTC time.
4. THE Reminder_Store SHALL store the Series_Frequency field as a string with one of the following values: `never`, `weekly`, `monthly`, `yearly`.
5. WHEN the user edits an existing reminder, THE Reminder_Form SHALL pre-select the current Series_Frequency value stored on the reminder record; IF no value exists on a legacy reminder (created before this feature) or the value is null, THEN THE Reminder_Form SHALL treat the value as `never` and pre-select "Never".
6. THE Reminder_Form SHALL enforce that exactly one Series_Frequency option is selected before allowing form submission; IF no option is selected, THEN THE Reminder_Form SHALL prevent submission and display a localized validation message indicating that a frequency selection is required.
7. WHEN the reminder record is included in a sync push payload, THE Sync_Service SHALL include the Series_Frequency field value in the push request body; WHEN a pulled reminder record contains a null or missing Series_Frequency value, THE Sync_Service SHALL default the field to `never` before storing locally.

### Requirement 2: Generate Series Occurrences on Calendar Event Creation

**User Story:** As a user, I want calendar events to be automatically created at the specified repetition interval when I create a reminder-type event from a reminder with a series, so that I do not need to manually create each recurring event.

#### Acceptance Criteria

1. WHEN the user creates a calendar event with `eventType` set to "reminder" and the referenced reminder has Series_Frequency set to a value other than `never`, THE Event_Store SHALL generate Series_Occurrence records for all future repetition dates from the Source_Event's `startDay` through the end of the Current_Year (December 31), excluding the Source_Event's own `startDay`.
2. WHEN Series_Frequency is `weekly`, THE system SHALL generate one Series_Occurrence for every 7 calendar days after the Source_Event's `startDay`, until December 31 of the Current_Year is reached or exceeded. The first occurrence is at `startDay + 7 days`, the second at `startDay + 14 days`, and so on.
3. WHEN Series_Frequency is `monthly`, THE system SHALL generate one Series_Occurrence on the same day-of-month as the Source_Event's `startDay` for each subsequent month, until December 31 of the Current_Year is reached or exceeded. IF the target month has fewer days than the Source_Event's day-of-month (e.g., day 31 in a 30-day month), THEN THE system SHALL use the last day of that month as the occurrence date.
4. WHEN Series_Frequency is `yearly`, THE system SHALL generate one Series_Occurrence on the same month and day as the Source_Event's `startDay` for each subsequent year, stopping when the computed date exceeds December 31 of the Current_Year. IF the Source_Event falls on February 29 (leap year) and the target year is not a leap year, THEN THE system SHALL use February 28 as the occurrence date.
5. EACH Series_Occurrence SHALL be a complete calendar event record with: a new client-generated UUID as `id`, the same `eventType`, `eventTypeId`, `startTime`, `endTime`, `totalHours`, `notes`, and `alertOffsets` values as the Source_Event, `startDay` and `endDay` adjusted to the computed repetition date (preserving the same day span as the Source_Event), `modifiedAt` set to the current UTC timestamp, `syncedAt` set to null, and `isDeleted` set to false.
6. WHEN Series_Frequency is `never`, THE Event_Store SHALL create only the single calendar event the user explicitly defined (current behavior preserved), without generating any Series_Occurrence records.
7. THE Source_Event itself SHALL be persisted as a standard calendar event in the Event_Store with no special marker distinguishing it from its Series_Occurrences — all events (source and occurrences) are independent records.
8. THE system SHALL generate a maximum of 366 Series_Occurrence records per single event creation to prevent unbounded generation in edge cases (e.g., weekly frequency from January 1).

### Requirement 3: Generate Series Occurrences on Reminder Modification

**User Story:** As a user, I want the system to handle repetition changes when I modify a reminder's series frequency, so that my calendar reflects the updated recurrence pattern.

#### Acceptance Criteria

1. WHEN the user modifies a reminder and changes the Series_Frequency from one value to another (including from `never` to a repeating value, or from a repeating value to `never`), and the reminder is referenced by one or more non-deleted calendar events whose `startDay` falls within the Current_Year, THE Reminder_Form SHALL display the Propagation_Modal asking the user whether to update existing calendar events.
2. THE Propagation_Modal SHALL inform the user that: the reminder's repetition frequency has changed, existing calendar events for the Current_Year may be affected, and the user may choose to regenerate occurrences or leave existing events unchanged.
3. WHEN the user confirms propagation after changing Series_Frequency from a repeating value to `never`, THE Event_Store SHALL soft-delete (set `isDeleted` to true, `modifiedAt` to current UTC, `syncedAt` to null) all calendar event records that reference the modified reminder, have `startDay` within the Current_Year, and have `startDay` strictly after the earliest non-deleted Source_Event's `startDay` for that reminder within the Current_Year.
4. WHEN the user confirms propagation after changing Series_Frequency from `never` to a repeating value, THE system SHALL identify the earliest non-deleted calendar event referencing the modified reminder within the Current_Year as the Source_Event, and generate new Series_Occurrences from that Source_Event through December 31 of the Current_Year using the new frequency, copying the Source_Event's `eventType`, `eventTypeId`, `startTime`, `endTime`, `totalHours`, `notes`, and `alertOffsets` fields to each generated occurrence while assigning a new UUID as `id`, the computed recurrence date as `startDay` and `endDay` (preserving day span), `modifiedAt` to current UTC, `syncedAt` to null, `isDeleted` to false, and skipping any date that already has a non-deleted calendar event referencing the same reminder.
5. WHEN the user confirms propagation after changing Series_Frequency from one repeating value to another (e.g., `weekly` to `monthly`), THE system SHALL soft-delete (set `isDeleted` to true, `modifiedAt` to current UTC, `syncedAt` to null) all existing non-deleted calendar events referencing the modified reminder with `startDay` strictly after the earliest Source_Event's `startDay` within the Current_Year, then generate new Series_Occurrences from the earliest Source_Event using the new frequency through December 31 of the Current_Year, copying the same fields as specified in criterion 4.
6. WHEN the user declines propagation in the Propagation_Modal, THE Reminder_Form SHALL save only the reminder record modification (updated Series_Frequency) without creating, modifying, or deleting any calendar event records.
7. IF the reminder has no non-deleted calendar events in the Current_Year, THEN THE Reminder_Form SHALL save the reminder modification and navigate back to the Reminders_Page without displaying the Propagation_Modal.
8. IF only non-series fields of the reminder are modified (name, icon, backgroundColor) without changing Series_Frequency, THEN the existing Propagation_Modal behavior from Requirement 7 of gh18-calendar-shift-reminder-improvements SHALL apply (propagation of display field timestamps), and the Series_Frequency logic SHALL NOT trigger.
9. IF the user modifies both Series_Frequency and non-series fields (name, icon, backgroundColor) in the same edit, THEN THE Reminder_Form SHALL display only the Series_Frequency Propagation_Modal (criteria 1–5), and upon user confirmation the generated Series_Occurrences SHALL reflect the updated non-series field values from the saved reminder; upon user decline, only the reminder record is saved (no calendar event modifications).

### Requirement 4: Series Occurrence Day Span Preservation

**User Story:** As a user, I want generated series occurrences to preserve the same day span as the original event, so that multi-day reminder events repeat correctly.

#### Acceptance Criteria

1. WHEN the Source_Event spans multiple days (endDay > startDay), EACH Series_Occurrence SHALL compute its `endDay` by adding the day difference (Source_Event `endDay` minus Source_Event `startDay`, measured in calendar days) to the occurrence's computed `startDay`, formatted as a YYYY-MM-DD date string.
2. WHEN the Source_Event is a single-day event (endDay equals startDay), EACH Series_Occurrence SHALL have `endDay` equal to its `startDay`.
3. THE system SHALL preserve `startTime` and `endTime` identically (same integer values, range 0–1439) on all Series_Occurrences — only `startDay` and `endDay` are adjusted for each repetition.
4. WHEN the Source_Event has a day span of 0 days (endDay equals startDay) and `endTime` is less than or equal to `startTime` (midnight-crossing event), EACH Series_Occurrence SHALL preserve `endDay` equal to `startDay` plus 1 day, consistent with the `computeEndDayForShift` rule that treats endTime <= startTime as crossing midnight.

### Requirement 5: Display Series Frequency on Reminder Card

**User Story:** As a user, I want to see the repetition frequency on the reminder card, so that I can quickly identify which reminders have a series configured.

#### Acceptance Criteria

1. THE Reminder_Card SHALL display the Series_Frequency value as a localized label on a second line below the reminder name, using the following mapping: `weekly` → "Every week" / "Cada semana", `monthly` → "Every month" / "Cada mes", `yearly` → "Every year" / "Cada año" (rendered in the user's active language).
2. IF the reminder's Series_Frequency is `never` or the field is absent (legacy reminder), THEN THE Reminder_Card SHALL NOT render the frequency label and SHALL NOT reserve vertical space for it (the card height remains the same as a card without a series).
3. THE Series_Frequency label SHALL be rendered using the `labelSmall` typography style on Android (Material3) and body small size (12px) on React Web, with the `text-secondary` color (`#6B7280` in light mode, `#9CA3AF` in dark mode), positioned below the reminder name within the content area and left-aligned with the name text.
4. WHILE a reminder has `isActive` set to false (deactivated state), THE Series_Frequency label SHALL inherit the same reduced opacity applied to the rest of the Reminder_Card content.

### Requirement 6: Series Data Synchronization

**User Story:** As a subscribed user, I want the series frequency field to synchronize across devices, so that my reminder repetition configuration is consistent on all platforms.

#### Acceptance Criteria

1. THE Sync_Service SHALL include the `seriesFrequency` field (value: one of `never`, `weekly`, `monthly`, `yearly`) when pushing reminder records to the backend API and SHALL accept and persist the `seriesFrequency` field when pulling reminder records from the API; IF the pull response contains a null or missing `seriesFrequency` for a record, THEN THE Sync_Service SHALL treat the value as `never` when persisting locally.
2. THE backend API SHALL store the `seriesFrequency` field as a non-nullable string column (varchar, maximum 10 characters) on the Reminder entity, with a database migration default of `never` applied to all existing records; IF a push request contains a record with a null or missing `seriesFrequency` field, THEN THE backend API SHALL treat the value as `never` for that record.
3. IF a push request contains a record with a `seriesFrequency` value that is not one of the valid values (`never`, `weekly`, `monthly`, `yearly`), THEN THE backend API SHALL reject the entire push batch with a validation error response indicating the invalid field value.
4. WHEN a reminder with a Series_Frequency other than `never` is pulled from the backend and the local device does not yet have the corresponding Series_Occurrences, THE system SHALL NOT automatically generate occurrences on pull — occurrences are generated only when a user explicitly creates a calendar event on that device or confirms propagation after a frequency change.
5. ALL Series_Occurrence calendar events generated locally SHALL synchronize to the backend as standard calendar event records via the existing calendar event sync mechanism, without any special handling.

### Requirement 7: Cross-Platform Consistency for Reminder Series

**User Story:** As a user, I want the reminder series feature to work identically on both React Web and Android, so that I have a consistent experience regardless of platform.

#### Acceptance Criteria

1. THE Reminder_Form SHALL present the same Series_Frequency options (Never, Every week, Every month, Every year) in the same order, with the same default selection ("Never"), on both React Web and Android platforms.
2. THE series generation logic SHALL produce the same set of Series_Occurrence dates for the same Source_Event and Series_Frequency on both platforms: given the same `startDay`, the same frequency, and the same Current_Year boundary, both platforms SHALL compute identical occurrence `startDay` values. WHEN a monthly occurrence would land on a day that does not exist in the target month (e.g., source `startDay` is the 31st but target month has 30 days), both platforms SHALL clamp to the last day of that target month. WHEN a yearly occurrence has source `startDay` of February 29 and the target year is not a leap year, both platforms SHALL clamp to February 28.
3. THE Reminder_Card SHALL display the Series_Frequency label in the same position (below the reminder name) and using the same visibility rule (hidden when `never`) on both platforms, rendered with each platform's native UI components.
4. WHEN the user changes the language setting to Spanish or English, THE Reminder_Form frequency options and THE Reminder_Card frequency labels SHALL render in the selected language on the next UI render cycle without requiring an application restart on both platforms.
5. THE Propagation_Modal for series frequency changes SHALL present the previous frequency value, the new frequency value, and the count of existing calendar events that will be affected, along with the same two user options (confirm propagation, decline and keep existing occurrences) on both platforms, with platform-native dialog styling.
